## 1. 我理解这道题在考什么

题面是「按 MCP 协议实现 3 个 server + 1 个 agent，输出一份矿权日报」。
但真正被考的不是「你会不会用 MCP SDK」——那个查文档半小时就能写出来。
**被考的是三件事，而且它们都有明确的失败信号：**

| 真正在考什么 | 做砸了长什么样 |
|---|---|
| **协议层**：你是否理解 MCP 的边界在哪 | 写了个只能自己调自己的私有客户端，换个宿主就接不进去 |
| **数据层**：你怎么处理「拿不到真实数据」 | 造假数据但不标注，或者一句「因数据源限制无法演示」 |
| **可靠性**：LLM 编数字时你怎么办 | 简报读起来很专业，但里面的数字有一半是编的 |

这三条决定了整份作业的走向，下面逐个展开。

## 3. 三个关键设计决定

这三个是这道题里我真正做了判断的地方，其余的（用什么库、怎么写循环）都是次要的。

### 3.1 可恢复的错误是返回类型，不是异常

**问题**：MCP SDK 出于安全考虑，会把工具抛出的未预期异常的**细节全部屏蔽**，
客户端只能收到一句 `Error executing tool get_price`。

**为什么这很致命**：我最初就是这么写的 —— 未知品种时抛 `ValueError("未收录品种，可选：…")`。
Agent 收到的是那句无信息量的通用错误。它不知道：
- 错在哪（是品种名写错了？还是日期格式错了？）
- 该怎么改（**有没有别的品种可选？**）
- 要不要重试

于是它只能放弃，或者更糟 —— **瞎猜一个**。

**做法**：引入 `ToolFailure`，把可恢复的业务错误建模成**合法的返回类型**：

```python
class ToolFailure(BaseModel):
    ok: Literal[False] = False
    error: str                      # 人话描述
    hint: Optional[str] = None      # 建议的下一步
    available: list[str] = []       # 可选枚举值
```

对应的，所有成功返回体加上 `ok: Literal[True] = True`，
这样 `ok` 字段就是一个**可判别联合（discriminated union）**的判别式，
Agent 侧 `if not payload["ok"]: 读 hint 重试` 就够了。

**边界划在哪**：真正的程序缺陷（除零、KeyError、网络超时）**仍然抛异常**。
判据是「这是调用者能通过改参数解决的，还是不能」。能 → `ToolFailure`；不能 → 让它崩。

**验证**分两处，职责不同：

- `scripts/smoke_servers.py` 打 5 条错误路径（不存在的 URL / 空 query /
  未知品种 / `days=0` / 不存在的 PDF），**把返回体原样打印出来给人看** ——
  「错误信息说不说人话」这件事最终得靠眼睛判断。
- `tests/test_mcp_protocol.py::test_recoverable_errors_carry_hint_and_available`
  才是**断言**：`ok is False` 且 `error` / `hint` / `available` 三者都非空。

（分开是有意的：前者是给人看的证据，后者是给 CI 看的闸门。
只有后者会阻止回归，只有前者能说服人「这条错误信息真的有用」。）

---

### 3.2 LLM 是增强，不是依赖

**问题**：`RUN.md` 承诺「5 分钟跑通」。如果跑通的前置条件是「先去申请一个 API key」，
这个承诺就不成立 —— 评委很可能连 key 都不想配就想看效果。

**做法**：把能力边界划死。

| 环节 | 谁来做 | 为什么 |
|---|---|---|
| 查询规划（拆检索词/选报告/选行情序列） | LLM，**失败回落本地打分** | 模型更会抓专有名词，但本地打分已足够 |
| 取数（调 3 个 MCP 工具） | **确定性代码** | 工具集固定，让模型自由选只是引入不确定性而没有任何收益 |
| 统计 / 趋势 / 单位归一化 | **确定性代码** | 硬事实，不该由模型即兴发挥 |
| 风险识别 | **确定性规则** | 模型很擅长生产「听起来合理但无出处」的风险，那正是日报最不该有的东西 |
| 叙述成文 | LLM，**失败回落模板** | 这是模型真正不可替代的地方 |
| 数字引用校验 | **确定性代码** | 见 3.3 |

**没 key 时走 `render_template_draft()`，用的是同一份证据、同一套数字**，
只是把「模型组织语言」换成 f-string 拼装。
所以有 key 和没 key 跑出来的简报，**数字部分逐字相同** —— 这一点可以用 diff 自己验证。

**为什么不让模型自由选工具**：三个数据源是固定的，
用 function calling 让模型决定「这次要不要查价格」，只会引入不确定性而没有收益。
**工具编排的确定性，是这个 Agent 能在没有 API key 时依然跑出完整结果的前提。**

### 3.3 数字引用校验：draft → verify 的回头边

**问题**：即便提示词里写了三遍「只使用给定证据里的数字」，
模型仍然会在长文里滑进去几个**精确但虚构的数字** —— 比如把「跌 22.8%」写成「跌 22.5%」，
或者给一个证据里根本没有的总量。

这是幻觉最危险的形态：**它看起来最专业。**

**做法**：草稿写完后，`verify` 节点把草稿里**出现的每一个数字**拿去证据里查一遍。
查不到就带着「哪些数字没有出处」的反馈打回重写一次；
第二次还编，就把可疑数字列进「数据质量告警」而不是假装没看见。

这是 **faithfulness 的最低成本实现**：不判断句子对不对，只判断数字有没有出处。

**⚠️ 这里有个几乎必然踩、踩了就完全失效的坑**：
证据是 JSON，数值一律是 `233.0` / `145650.0`；而草稿写的是人话 `233` / `145,650`。
如果归一化只做 `rstrip("0")`，`"233.0"` 会变成 `"233."`（**留着小数点**），
于是 `233` 匹配不上 `233.0` —— 校验器会把**每一个照抄证据的数字**都判成幻觉，
然后驱动模型去改一个本来正确的数字。**越改越糟。**

修法是把小数点和尾零分开处理：

```python
if "." in plain:
    trimmed = plain.rstrip("0").rstrip(".")   # "233.0" -> "233"
```

我第一次真跑就是这个症状：告警里列了 `233、64,300、208、172,800、145,650` ——
**全部都是证据里逐字存在的数字**。如果不逐条核对而是直接「修复」，会把这套机制彻底改坏。

**设计取向**：宁可漏报也不误报。
误报会让模型去改一个正确的数字，比漏一个幻觉更糟。
所以单位换算、四舍五入、千分位差异都算命中。

## 4. 三个 MCP server 的设计

### 4.1 为什么是三个 server，而不是一个

按**数据来源的外部边界**切，而不是按功能切。
新闻（文本检索）、储量（PDF 解析）、行情（时序数据）的依赖、失败模式、
更新频率完全不同：新闻 server 挂了不该影响价格查询，PDF 解析要装 pypdf 而行情不需要。

**一个 server 也可以拆成一个函数库** —— 但那样就丢掉了「能被 Claude Desktop
单独接进去」这个 MCP 的核心价值。三个 server 意味着使用者可以只接他需要的那一个。

### 4.2 `mining-news-mcp`

- **自写 BM25**，不是 `rank_bm25`：需要**字段权重**（标题命中 4× 于正文顺带提一句）
  和 **CJK 二元组分词**（中文没有空格，标准分词器对「皮尔巴拉锂矿」这种连写会失效）。
- **时间衰减**：`exp(-λ·Δt)`，把相关性分数乘上去。矿业新闻的时效性极强。
- **`corpus_now()` —— 这是最容易翻车的一处**：
  离线语料里最新一条是 `2026-08-26`，而系统真实日期是 `2026-10-14`。
  如果 `days=7` 按真实 now 过滤，结果**恒为空，整个 demo 直接哑火**。
  所以把「语料内最新发布时间」当作数据集的时间基准，并在 `provenance.as_of` 里如实透出。
  **live 模式下 `as_of` 就是真实当前时间** —— 两种模式语义一致：
  「相对于数据最新时点的近 N 天」。
- **`source_verified` 一路透传到产出**：抓取时被反爬拦截的链接标 `search_only`，
  Agent 会把它单独列成一条低级别风险提示（「引用前建议人工打开确认」）。
  **把数据的不确定性透传到最终交付物，而不是中途藏起来。**

### 4.3 `mineral-pdf-mcp` —— 全项目最硬的一块

**为什么难**：四份报告是**四种不同的表格排版**：

| 报告 | 难点 |
|---|---|
| Barrick | **并排分组表头** `MEASURED (M) INDICATED (I) (M)+(I) INFERRED`，金/铜两组资源量左右并排在同一张表 |
| Newmont | 单位是 `000 tonnes` 而非 `Mt`；**按行**（每行一个类别） |
| Pilbara 2016 | JORC 多金属同表，单位混用 `Mt` / `% Li2O` / `t` |
| Pilbara 2015 | 同上变体，钽用 `Mlb`（百万磅）计量 |

解析思路是**基于字符位置**的：按空白切出单元格 → 按字符偏移堆叠多层表头
→ 把每个数字按**中心点**分配到最近的列 → 按列组读数。

**踩过的四个坑（每一个都让整张表读错，而不是差一点点）**：

1. **`tonnes?\b` 匹配到了 `g/tonne`** —— `Grade (g/tonne)` 被判成吨位列，
   整表数字错位。修法是**单位括号优先于关键词**。
2. **大写水印规则误杀 Barrick 的分组表头** —— 「整行大写且长度 > 40」这条规则
   把 `MEASURED (M)    INDICATED (I)    INFERRED` 也判成了水印，
   于是所有分组信息丢失。区分点是**水印行没有连续空格**（是排版时硬塞进去的整串），
   而表头行靠列间距对齐、必然含两个以上连续空格。
3. **`Tonnes Grade Contained` 中间只有一个空格** —— 粗切只认「两个以上空格」，
   于是三个列名被并成一格，列名里三处出现 "Contained"，全部被判成金属量列。
4. **向后扫描吞掉上一张表的脚注** —— `Altura Mining Limited, February 2016` 这行
   覆盖到了单位行上，列名成了 `Limited, Tonnes (Mt)`。

**弃权机制**：`ABSTAIN_CONFIDENCE = 0.55`。
整体置信度低于阈值、或 PDF 无文本层（扫描件，未接 OCR）时**主动交白卷**。

> 这是整个项目里我最有把握的一条产品判断：
> **在矿业尽调场景里，一个错的储量数字比一个空的储量章节危害大得多。**
> 错的数字会被写进估值模型，而空的章节会被人去补。

### 4.4 `lme-price-mcp`

- **别名表是显式枚举的**：「锂价」到底指碳酸锂还是锂辉石，靠字符串相似度猜不准 ——
  那就把主要叫法一条条列出来（`碳酸锂`/`电碳`/`锂`/`lithium`）。
- **非交易日回退**：请求日没有报价时回退到最近一个交易日，
  并**如实透出** `date`（实际日期）和 `requested_date`（请求日期），
  而不是假装那天就是请求日。
- **上游下游联动**：Agent 的查询规划里，问到「锂」会把碳酸锂**和**锂辉石一起拉进来。
  只看下游碳酸锂会漏掉成本端，日报里这两个价格要一起看才有意义。

## 5. Agent 编排（LangGraph）

```
                    ┌─ gather_news ────┐
START → plan ───────┼─ gather_resources┼→ assess_risks → draft → verify ─┬→ render → END
                    └─ gather_prices ──┘                              └→ draft（回炉一次）
```

**三个编排决定**：

1. **三个取数节点并行扇出。** 它们之间没有依赖，串行跑等于白等两倍时间。
   LangGraph 的并行分支天然支持 —— 三个节点写 state 里三个不同的键。

2. **`trace` / `warnings` 挂了 `operator.add` reducer。**
   这一点不挂会直接抛 `InvalidUpdateError`：三个节点在**同一个超步**里
   并行写同一个通道，属于未定义行为。挂上 reducer 后语义变成「追加」。

3. **节点用真正的 `async def` 包装函数，不是 lambda。**
   LangGraph 靠 `iscoroutinefunction` 判断该 await 还是把返回值当 state 更新，
   而 `lambda s: node_gather_news(s, hub)` 只是个普通函数 ——
   返回的 coroutine 会被当成 state 字典丢掉。
   现象是各取数节点**根本没执行**（"coroutine was never awaited"）且 state 全空。
   这是个不报错、只是静默不干活的失败模式，很值得记住。

**`hub` 由闭包注入，不进 state**：它持有三个子进程会话，不可序列化。
`MCPHub` 用 `AsyncExitStack` 在整个简报生成期间持有会话 ——
一次简报要调 10~12 次工具，每次重启进程纯属浪费。

## 6. 风险提示为什么要用规则生成

日报的「风险提示」是最容易变成**废话重灾区**的一节。
模型写出来的典型长这样：「需关注锂价波动风险」「政策变化可能带来不确定性」——
听起来专业，但没有任何信息量，而且**没有出处**。

我的做法是：**风险提示 100% 由确定性规则从数据里生成**，每条都必须挂得住
一个具体数字或事实：

| 规则 | 触发条件 | 输出形态（真实样例） |
|---|---|---|
| 价格显著下行 | 近 90 天跌幅 ≤ -10% | 「近 90 天由 144,650 跌至 111,650 CNY/t，跌幅 22.8%，区间最低 109,050（2026-10-12）」 |
| 波动率偏高 | 日收益率标准差 ≥ 1.5% | 「报价噪音大，单日涨跌代表性有限」 |
| 储量数据时效性 | 生效日 ≤ 2016 年 | 「生效日 2015-06-30（JORC 2012），标注为历史估算，不宜直接与最新披露对比」 |
| 新闻面负面 | `sentiment == negative` | 引新闻原标题 + 摘要 + 链接 |
| 引用未实测 | `source_verified == search_only` | 「原文链接抓取时未能实测返回 200，引用前建议人工打开确认」 |

模型能做的只是**把这些已成立的条目润色成句子**。

**并且：模型可以润色风险，但不能决定「哪条风险不告诉你」。**
`render` 节点会逐条比对草稿 —— 凡是规则生成的风险没在草稿里出现的，
一律追加到「补充风险提示」里。

（这里的匹配必须是**模糊**的：规则写「Pilbara Minerals Limited 储量数据时效性」，
草稿写「PLS 储量数据时效性」，整串匹配必然失败，结果同一条风险在正文和附录
各出现一遍，读起来像两条不同的风险。所以指纹取「标题抹掉空白」+「标题最后一段」
+「详情里的日期」。）

## 7. 数据策略：fixture 的真实性边界

**核心原则：用离线样本做 demo 时，必须让评审者一眼看清「哪些是真的、哪些是造的」。**

| 数据 | 真实性 |
|---|---|
| 新闻标题 / 链接 / 机构 / 时间 | ✅ 真实抓取，可点开核验 |
| 新闻摘要与正文 | ⚠️ 对公开事实的中文改写，非原文转载（版权考虑） |
| 储量报告数值 | ✅ Barrick / Newmont / Pilbara / Altura 实际披露数据 |
| 储量报告 PDF 文件 | ⚠️ 按披露数据重新排版生成（原文件版权/链接失效） |
| 价格锚点 | ✅ 公开行情 |
| 价格日频序列 | ⚠️ 锚点之间按几何布朗运动插值 |

**两条自我约束**：

1. **每份 fixture 的 JSON 里都带 `data_origin` / `note` / `_meta` 字段说明同样的事。**
   文档会被忽略，字段不会。
2. **价格 `stats` 必须标注为「构造走势」**。`lithium_carbonate_cn` 近 90 天 -22.8%
   这个数字**是 fixture 的性质，不是 2026 年市场的性质**。
   **一个不说明来源的百分比，比没有百分比更危险。**

**PDF 为什么是重建的**：原始 PDF 要么有版权、要么链接早已失效。
但**表格的排版结构（列位、单位括号、分组表头、水印）是刻意照搬真实报告的样子做的** ——
解析器要解决的正是这些结构问题，所以这份 fixture 对「验证解析器」这个目的是有效的。

完整的真实性逐字段清单见 [../DATA_NOTES.md](../DATA_NOTES.md)。

## 8. 验证方法与结果

### 8.1 储量提取：字段级准确率 30/30

```bash
uv run python scripts/check_extraction.py
```

四份 PDF、每份 2~4 行、每行 3 个字段（矿石量/品位/金属量），共 **30 个字段，全部通过，
最大误差 0.00026%**（容差 ±5%）。误差非零的唯一来源是 Pilbara 的钽用 `Mlb` 计量，
ground truth 存的是换算后四舍五入到 2 位小数的吨数。

**为什么这个脚本必须有，而不是「我肉眼看了一遍没问题」**：
PDF 表格解析是本项目里**唯一一处输出无法被常识判断对错**的地方。
新闻检索差了能一眼看出来，价格算错单位很明显，但
「Indicated 铜 5,400 Mt @ 0.39% = 22.0 Mt」这种数字，**看起来永远是对的**。
不逐字段对账，就没有任何证据说明解析器能用。

### 8.2 测试：88 个用例，分五层

坏起来的原因不同，所以要分层测：

| 层 | 管什么 |
|---|---|
| `test_tableparse.py` | 解析算法。**每个用例都对应一次真实的踩坑**，删掉任何一条都意味着那个 bug 可能回归 |
| `test_servers.py` | 业务逻辑：排序、别名、错误信息说不说人话 |
| `test_mcp_protocol.py` | **真起子进程走 stdio JSON-RPC**。工具 schema 能不能序列化、返回值能不能过 `structuredContent`、子进程 stdout 有没有被日志污染 —— 这些只在协议层才暴露 |
| `test_agent.py` | 规划、数字引用校验、风险覆盖判定、模板渲染 |
| `test_extraction_accuracy.py` | 字段级准确率闸门 |

**协议层单独测的理由**：核心交付物之一是「这三个 server 能被 Claude Desktop 直接接进去」，
那句话只有在真过一遍 stdio 之后才成立。直接 import 调函数会把整层协议漏掉。


## 9. 口述稿

### 2 分钟版

> 这道题我做了 MCP 协议下的一套矿权日报系统：三个 MCP server 加固一个 LangGraph Agent。
>
> 但我想先讲三个我在做的时候做的判断，因为我觉得它们比代码本身重要。
>
> **第一个是可恢复错误的建模。** MCP SDK 会把工具抛出的异常的细节全部屏蔽掉，
> 客户端只能收到一句 "Error executing tool get_price"。我一开始就是这么写的，
> 结果 Agent 既不知道错在哪、也不知道可选值是什么，只能瞎猜。
> 所以我把可恢复的业务错误做成了**合法的返回类型**：`ok=false` 加 `hint` 加 `available`。
> 现在 Agent 能读到「未收录该品种，可选：碳酸锂、锂辉石、铜…」并自己改。
> 真正的程序缺陷仍然抛异常 —— 判据是「调用者能不能通过改参数解决」。
>
> **第二个是 LLM 的定位。** RUN.md 承诺 5 分钟跑通，那就不能有「先去申请个 key」这一步。
> 所以我把模型的能力边界划死了：模型只负责**规划检索词**和**叙述成文**，
> 取数、算统计、判趋势、挑风险全部走确定性代码。
> 没 key 时回落模板草稿，用的是**同一份证据、同一套数字**，只是行文更机械。
>
> **第三个是数字引用校验。** 我在 draft 和 render 之间加了一条回头边：
> 把草稿里出现的每一个数字拿去证据里查，查不到就打回重写一次。
> 这里我踩了一个几乎必然踩的坑 —— 证据是 JSON，数值是 `233.0`，
> 草稿是人话 `233`，我归一化时只做了 rstrip("0")，结果 `233.0` 变成 `233.` 带着个小数点，
> 于是**每一个照抄证据的数字都被判成了幻觉**。
> 我第一眼看到告警列了五个数字，差点直接去"修"，幸好核对了一下 —— 那五个全是证据里逐字存在的。
>
> 验证方面：储量提取做了字段级的对账脚本，四份 PDF 三十个字段全对，最大误差 0.00026%；
> 测试 88 个用例，分算法、业务、协议、Agent、准确率闸门五层，
> 其中协议层是真起子进程走 stdio 的，因为"能被 Claude Desktop 接进去"这个卖点
> 只有在真的过一遍协议之后才成立。

### 5 分钟版补充

在上面基础上再加三块：

**数据策略**：我用的是内置 fixture，离线可复现。但关键在于**标注**：
每份 fixture JSON 里都带 `data_origin` 字段说明哪些是真实抓取、哪些是合成的。
新闻标题链接时间是真实的，摘要是中文改写；储量数值是公开披露的，PDF 是按这些数值重建的；
价格的锚点是真实的，日频序列是按几何布朗运动插值的。
**我还特意让 `live` 模式直接启动报错** —— 因为真实抓取代码还没写，
让它跑起来只会把 fixture 数据标成 `data_origin="live"`。
一个标错来源的数据，比一个明确报错的服务危险得多。

**PDF 解析那块最硬**：四份报告是四种不同的表格排版 ——
并排分组表头、`000 tonnes` 单位、JORC 多金属同表、`Mlb` 计量。
我踩的四个坑每一个都让**整张表读错**而不是差一点点，
其中最典型的是 `tonnes?\b` 这条正则会匹配到 `g/tonne`，
把品位列判成吨位列。
还有一个错误处理的判断：解析置信度低于 0.55 或者 PDF 没有文本层时**主动弃权**。
在矿业尽调场景里，一个错的储量数字比一个空的储量章节危害大得多 ——
错的数字会被写进估值模型，空的章节会有人去补。

**架构上还有一个不报错的坑值得说**：LangGraph 判断节点要不要 await
靠的是 `iscoroutinefunction`。我一开始图省事写了
`lambda s: node_gather_news(s, hub)`，它返回一个 coroutine，
但 LangGraph 把它当成了 state 更新字典丢掉。
现象是三个取数节点**静默地什么都没干**，state 全空，不报任何错。
改成真正的 `async def` 包装函数就好了。

## 10. 可能的追问

**Q：为什么不用 function calling 让模型自己决定调哪个工具？**

因为工具集是固定的。一次矿权日报永远需要这三类数据，
让模型去决定「这次要不要查价格」只会引入不确定性而没有收益，
而且会让「没 API key 也能出完整简报」这个特性直接失效。

模型的真正价值在**规划检索词**（它更会抓 Pilbara / Pilgangoora / spodumene 这类专名）
和**组织叙述**，这两处我都用了它，并且都做了无 key 兜底。

**Q：你的 verify 只查数字，那编造的非数字事实怎么办？**

查不出来，这是这套机制的明确边界。我在文档里也写清楚了 ——
它是 faithfulness 的**最低成本实现**，不是完整方案。
要做到完整，需要把每个句子回指到 source span，成本高一个数量级，
对 24 小时的作业不划算。
但我至少覆盖了**最危险的那一类**：精确但虚构的数字，因为它看起来最专业。

**Q：如果给你更多时间，下一步做什么？**

按优先级：
1. **接 OCR**（`pypdf` 换成 `pdfplumber` + `paddleocr`），覆盖扫描件 ——
   这是当前最大的功能缺口，矿业报告里扫描件占比很高。
2. **把 `live` 模式真正实现**，特别是新闻抓取和 SMM 价格 ——
   现在 `data_origin` 和 `resolve_pdf_path` 对真实 URL 的处理路径都已经铺好了，
   只差最后那几个抓取函数。
3. **表格解析的泛化**。现在是把排版规则写死，更好的做法是
   先做版面聚类（识别表头区/数据区/列边界），再套规则。
4. **把 verify 升级成句子级的引用回指**。

**Q：这个 fixture 数据是真的吗？**

逐字段的真实性清单在 DATA_NOTES.md 里，**哪些是真的、哪些是造的写在明面上**。
一句话版本：新闻的标题链接时间是真实抓取的、摘要是中文改写；
储量数值是公开披露的、PDF 是按这些数值重建的；
价格的锚点是真实的、日频序列是插值的。

我特意把这层不确定性也透传到了产出里 ——
链接抓取时被反爬拦截的条目，Agent 会单独列一条「引用前建议人工打开确认」的风险提示。

**Q：为什么只做了第 2 题？**

因为三道题里只有 #2 把「协议层 + Agent 编排 + 数据可靠性」三件事压在一起。
我判断**把一道题做到能扛住追问，比三道都停在 demo 层面更有说服力**。
#1 本质是数据工程，#3 是 PDF 解析的对抗审核 ——
#3 的难点实际上已经被我在 #2 的 PDF server 里覆盖了一部分。

**Q：`MCPHub.call` 声明「永不抛异常」，这会不会掩盖 bug？**

会，所以这条约束只加在**工具调用**这一层，而且失败会被记录进 `hub.calls`，
最终渲染成简报末尾「工具调用记录」表里的 ❌ 行。
理由是：简报生成是一条流水线，某个数据源挂了应该降级成
「该章节标注数据不可得」，而不是让整份简报崩掉。
**失败被显式记录并展示给用户，而不是被吞掉。**
